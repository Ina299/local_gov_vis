# 取得処理のローカル通信診断（2026-10-13 JST）

自治体には再接続せず、同じクラウド環境内のループバック HTTP プロキシと HTTPS サーバーで診断しました。元の6ホストの停止記録は変更していません。テスト用の子プロセスだけにループバックの接続設定と一時CAを渡し、本番のプロキシ情報は継承・表示・保存しません。TLS検証は無効化していません。テスト用プロキシは `city.example.jp:443` のみ受け付け、転送先は固定のループバックサーバーです。

## 以前の実取得から分かること

高松市の試行は `2026-10-12T16:28:19.108Z` に開始され、保存済み manifest の更新時刻は同19.133919501秒でした。両時刻の差は約26msですが、通信単体の所要時間は当時記録しておらず、この差には保存処理も含まれます。ツールが報告したキュー作成を含むコマンド全体の所要時間は0.172339178秒で、設定した30秒の期限とは一致しません。

同じ最初の実行呼び出しで終了コード2が返り、manifest と一覧も保存されています。途中の実行セルの終了やエージェント終了で中断したことを示す証拠はありません。後の環境切断通知の後も同じ環境でシェルと作業差分を確認しました。ただしこの記録だけでネットワーク上の中断原因は断定できません。

`UND_ERR_ABORTED` だけから自治体の拒否とは判定できません。以前のログは下位のメッセージを保存していないため、過去の実通信をプロキシ403だったと再分類することもできません。

## ローカルの実通信で再現したこと

- 実際の native fetch が TLS の遅延ストリームを最後まで保存し、ハッシュ対象のバイトが残ってから子プロセスが正常終了する。
- ヘッダーが来ない場合、本文が途中で止まる場合は指定期限に達して停止する。
- 本文途中の接続切断は HTTP 200 受信後の通信障害として記録し、取得成功や拒否にはしない。
- 原典サーバーが返す403は原典HTTP拒否として停止する。
- 既存設定相当のローカルプロキシ経由でも正常なTLS取得は成功する。
- プロキシが CONNECT に403を返すと、Node 24 の native fetch は原典 Response を返さず `UND_ERR_ABORTED` を返す場合がある。
- Node v24.19.0 内蔵 Undici 7.29.0 では、プロキシが CONNECT 前に接続を切ると再接続ループを再現した。500msでアプリの期限が発火した後も接続が続き、10秒のテスト上限まで子プロセスが終了しなかった。標準APIの restore は元の dispatcher に戻すだけで、新規 dispatcher を破棄していなかった。

## 修正

資料ごとの専用 dispatcher を native fetch に渡し、必ず破棄します。環境の既存プロキシ設定は変更せず同じ意味で利用します。Undici 7 の CONNECT 前切断は回復不能として返す専用 clientFactory を使い、ループバックテストで CONNECT が1回だけで終了することを確認します。

従来はリダイレクトごとに30秒の期限がリセットされていました。1資料全体の単一期限へ変更し、リダイレクト待機も期限切れで中断します。ストリーム中断時には cancel のエラーで元の原因を上書きしません。

原因分類に `paused` と `failureKind` を追加しました。未特定の通信失敗とタイムアウトを自治体の拒否と表示しません。原典HTTP状態と、既知の固定形式から抽出できたプロキシHTTP状態は分離します。分類の変更でホスト停止を解除しません。

## 検証方法

`node --import tsx --test apps/crawler/tests/source-collection/*.test.ts` で mock による状態検証とループバック実通信の両方を実行します。PRのCIでも Node 20/24 の両方で同じテストを実行します。Node20/24のバージョン差があってもプロキシ・タイムアウト・終了処理を実通信で検証します。自治体URLをテスト内で取得することはありません。
